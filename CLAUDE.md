## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:

- When graphify-out/graph.json exists, use it before raw grep or whole-file reads for a code question: `graphify affected "<file or symbol>"` for impact and callers, `graphify explain "<file or symbol>"` for structure and the line of each symbol, `graphify path "<A>" "<B>"` for relationships; then read only those line ranges. Put this rule in every subagent prompt that explores code.
- Do not use natural-language `graphify query`: it matches keywords and returns mostly noise. If needed, pass `--seed <node> --budget 500`. Find literal strings (env keys, error codes, routes) with grep (`-l` first, capped output).
- Large Markdown files (tasks/, SPEC.md, docs, state files over ~5 KB): read one part with `.claude/bin/section <file> <heading | §n | --id ID | --toc>`, never the whole file.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when affected/explain/path do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.

## Spec layout

The root `SPEC.md` is only the index: project description, objective and scope, the generated Flows and Modules tables, and the Old references table (old `SPEC §n` / `Dn` refs → new file). Requirements live per business flow in `docs/flows/<flow>/`: `SPEC.md` (what the flow must do), `FLOW.md` (steps, sequence diagram, modules taking part; front matter `modules:`) and `RULE.md` (rules every change in the flow must keep). Rules that cover several flows live in `docs/global/`. Before working in a flow, read its `RULE.md` and `FLOW.md`. A new or changed requirement goes into the flow's `SPEC.md` (updated in place, plus one Change log line), or into a new flow folder with all three files; never into the root `SPEC.md`. A flow names modules, never files: file lists belong in the module docs. The module table of `FLOW.md` is generated from its `modules:` front matter (edit only the Role column, and name a symbol only when a rule depends on it). After adding or changing a flow, run `.claude/bin/module-index` (it regenerates the root tables and the flow module tables). Put this rule in every subagent prompt that writes specs or explores code.

## Module index

`MODULES.md` (generated by `.claude/bin/module-index`) maps every app module to its folder and its doc in `docs/modules/`. To find where a feature, bug or task lives, read it first, then the module doc, then graphify. After changing code in a module, update its doc and run `.claude/bin/module-index`; `--check` must print nothing before a commit. Put this rule in every subagent prompt that explores code.
