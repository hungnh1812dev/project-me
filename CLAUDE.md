## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:

- When graphify-out/graph.json exists, use it before raw grep or whole-file reads for a code question: `graphify affected "<file or symbol>"` for impact and callers, `graphify explain "<file or symbol>"` for structure and the line of each symbol, `graphify path "<A>" "<B>"` for relationships; then read only those line ranges. Put this rule in every subagent prompt that explores code.
- Do not use natural-language `graphify query`: it matches keywords and returns mostly noise. If needed, pass `--seed <node> --budget 500`. Find literal strings (env keys, error codes, routes) with grep (`-l` first, capped output).
- Large Markdown files (tasks/, SPEC.md, docs, state files over ~5 KB): read one part with `.claude/bin/section <file> <heading | §n | --id ID | --toc>`, never the whole file.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when affected/explain/path do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.

## Spec layout

The root `SPEC.md` is the index: project description, objective, scope, and the generated Docs table (every global doc, app and flow with the old SPEC ids it replaced: an old `SPEC §n` / `Dn` / `§12-n` ref resolves through its Replaces column). Three scopes, each with `SPEC.md` (requirements, decisions), `FLOW.md` (steps, processes) and `RULES.md` (rules): a business flow in `docs/flows/<flow>/` (rules of that flow only; `FLOW.md` front matter `modules:`), an app in `docs/apps/<cms-api|cms-admin|web>/` (what every flow of the app shares), and `docs/global/` (`RULES.md`, `FLOW.md`, `DECISIONS.md` with the index of every `D` id, `ACCEPTANCE.md`, `reference/` with definitions and values only). Every section of a global or app `RULES.md` / `FLOW.md` says `Applies to:` (all flows, or the flows it covers). Before working in a flow, read `docs/global/RULES.md`, the `RULES.md` of each app the change touches and the flow's `RULES.md` and `FLOW.md`. A new or changed requirement goes into the flow's `SPEC.md` (in place, plus one Change log line), or a new flow folder with all three files; a rule shared by every flow of one app goes into that app's `RULES.md` / `FLOW.md`; one shared by several flows across apps goes into `docs/global/RULES.md` / `FLOW.md`, naming the flows; never into the root `SPEC.md`. A flow names modules, never files (file lists belong in the module docs); its `FLOW.md` module table is generated from `modules:` (edit only the Role column). Then run `.claude/bin/module-index`; `--check` must print nothing. Full steps: `docs/global/FLOW.md` "Where a change goes". Put this rule in every subagent prompt that writes specs or explores code.

## Module index

`MODULES.md` (generated by `.claude/bin/module-index`) maps every app module to its folder, its doc in `docs/modules/`, the doc status (`complete`, `draft`, `missing`) and the flows it takes part in. To find where a feature, bug or task lives, read it first, then the module doc, then graphify. After changing code in a module, update its doc and run `.claude/bin/module-index`; `--check` must print nothing before a commit. Put this rule in every subagent prompt that explores code.
