# web: spec

Part of the [project spec](../../../SPEC.md). App `web`: [SPEC.md](SPEC.md) · [FLOW.md](FLOW.md) · [RULES.md](RULES.md). In these files a section without an `Applies to:` line covers every flow that touches this app.

## Behaviour

apps/web is the public site on `domain.com`: Next.js 16 App Router run as a standalone Node server. Server Components fetch content through GraphQL from `APP_API_URL`; the browser calls only the BFF Route Handlers under `/api/v1` on the web origin ([stack-and-commands.md](../../global/reference/stack-and-commands.md), [api-contract.md](../../global/reference/api-contract.md) "Web BFF").

User answers (2026-11-12): Q-WEM1..Q-WEM5 below.

- **WEB-1 Three API layers.**
  - **Server RESTful** (`apis/server/restful`, `server-only`): the one HTTP client of the Next server to cms-api; methods GET, POST, PUT, PATCH, DELETE; axios with its `fetch` adapter over the Next.js `fetch`, cache options passed through `fetchOptions`, so the Next data cache applies (Q-WCA1). The first task proves a cache hit (POST with a Bearer header); if it cannot, the layer uses native `fetch` behind the same interface. Base URL `APP_API_URL`, paths only from `API_ENDPOINTS`, timeout `API_TIMEOUT_MS`, never follows a redirect, per-call headers and cache option (WEB-4), its failures raised in the shared API error shape (WEB-10); no mock (WEB-5). The BFF cms-api client (`cmsApiClient`) moves onto this layer in its own security-gated task, with its manual redirect, single `X-Forwarded-For` (plus `CLIENT_IP_HEADER`) and `Set-Cookie` reading unchanged (Q-WCA9). The Cloudflare siteverify call stays as it is.
  - **Server GraphQL** (`apis/server/graphql`): one POST to `API_ENDPOINTS.GRAPHQL` through the server RESTful layer; content reads carry the API token (WEB-2); a signed-in visitor's CV refetch keeps that visitor's access token, never cached (D21); the answer is unwrapped by `GraphqlResponse.rules`; it owns the mock fallback, above the fetch (WEB-5).
  - **Client RESTful** (`apis/client`): the same five methods for the browser, only to the BFF under `BFF_BASE_PATH`; no token, no mock, no cache option, never a cms-api URL (D21); every failure comes back in the shared API error shape (WEB-10).
- **WEB-2 API token and base URL** (Q-WCA2, Q-WCA4). Server GraphQL content reads send a cms-api API token (D5) as Bearer from the server-only runtime key `APP_API_TOKEN`: never in a `NEXT_PUBLIC_*` key, never sent to the browser, never logged. Required in production (start fails when missing or not `ak_live_…`); optional outside production, where reads without it run anonymously and WEB-5 covers missing data. The token's read profile is the `public` role's and no wider: sensitive fields (public-site Q5) stay masked, because one cached answer serves every visitor. Its scope is one entry, `{ "subject": "*", "action": "read" }`, on every stack and in production (Q-WCT1): the read-only creating account bounds it (D5), so it reads published content of the types that account reads, with that account's masks, and never a system subject or a draft; a content type web starts reading needs no new token. The web env key `APP_API_URL` replaces `API_INTERNAL_URL` (same value and meaning: cms-api as the Next server reaches it).
- **WEB-3 Text from cms-api** (Q-WCA10, Q-WCA11). No user-facing text in web source: `configs/Copy.constants.ts` (`COPY`) is removed. Every text comes from the typed single types of the page queries (public-site PS-1), English only, no locale argument. Server Components get it as props; client components (sign-in dialog, account menu, status card, CV view) get it from the server render through one text context set by the layout, never by their own fetch. Texts with values use named placeholders (`{name}`, `{seconds}`) filled by one formatter in `utils/`; plural forms are separate keys (`…One`, `…Other`). Only exception (Q-WCA7, Q-WCP3): a built-in last-resort text set of about 9 strings (error title, description and retry; not-found title and description; the status card words checking, operational, unreachable and check again), used only by the global error page and the not-found page when the shell text cannot load, and by the status card when `statusPageText` cannot load (PS-2).
- **WEB-4 Cache per call** (Q-WCA5). Every server fetch sets its own revalidate seconds; default 180 s (a named constant), a query may set its own; visitor-token calls are `no-store`. `WEB_REVALIDATE_SECONDS` no longer sets a global value: it is an optional override of every call's value, set to `0` by the dev and smoke stacks only; deploy config drops it (patch note).
- **WEB-5 Mock fallback** (user answer 1, Q-WCA6, changed 2026-11-12 Q-WEM1..Q-WEM5). Mocks fill only content reads of the server GraphQL layer (`runContentQuery`); the server RESTful layer, the BFF, the client RESTful layer and calls with a visitor's token never get one. The mocks live in the server GraphQL layer; `MockView.ts` is the one file that imports them and maps a flat, unique, typed **mock key** to its data (user decision; overrides code-standards §2 "mock data in test fixtures only" for this layer). Each root field of a content query names the mock key of its mock (by default the root field name), so a mock is chosen by key, never by operation name. **On** only where `APP_ENV` is not `production`, both at build and at runtime (WEB-9): with a `production` build the mock module is not in the bundle; elsewhere it is loaded with a dynamic `import()` on the first fallback, and never where the runtime `APP_ENV` is `production`. No other key turns the mocks on. **When:** only on an error: network, timeout, a non-2xx answer, a body that is not a GraphQL answer, or a GraphQL `errors` list, also with HTTP 200. An `errors` entry whose `path` starts with a root field fails that root field; an entry without `path`, or no `data`, fails every root field. A root field that answers null or empty without an error is real data: no mock, the section shows its empty state (a null page text single type: public-site PS-2). Where the mocks are on and cms-api rejects the whole operation, each root field is asked again alone before the mocks fill what still fails, so the root fields cms-api serves stay real (Q-WCP2). **Cache:** the fill happens above the fetch, after the Next data cache: a mock answer is never written to the data cache and has no revalidate seconds, and a render that used a mock is not kept as a cached page, so the next request asks cms-api again. Each use logs one warn line (operation, root field, mock key, error code), no data, no token. Where the mocks are off, a failed root field is `null` and listed as failed, and the section shows its error state. The mocks have exactly the shape of the committed query documents, so they also state what cms-api must serve.
- **WEB-6 Server data architecture.** Each page area's data is declared once, by the feature that owns it, as one named content query (GraphQL document, result type, revalidate seconds, the mock key of each root field in `MockView.ts`). A page loads its queries through one loader wrapped in React `cache`, so metadata and page share one call per render. No view or route file calls `fetch`, axios or GraphQL. A new page section is one root field or query in its feature, its mock and its view. Owners: `apis/server/restful` (HTTP), `apis/server/graphql` (GraphQL, token, mock fallback), a shell-text feature (named in `DESIGN web-content-api`), `features/status` (homepage text), `features/cv` (CV data and labels). Module map, names and file map: `DESIGN web-content-api`.
- **WEB-7 Role-based display, extension point** (user answer 2). One rule in `features/session` says whether the viewer (signed out, or signed in with the role slug `GET /api/v1/session` returns) may see a page, nav item or section that declares an optional `requiresRole`; nothing declared = visible to everyone (`header.nav.requiresRole` exists in the cms-api SDL). Display only, never access control: what a role may read stays guarded by cms-api (D3). No role-specific page in this change.
- **WEB-8 Scope and running alone.** No change in apps/cms-api or apps/cms-admin. `pnpm --filter @abyss/web dev` with cms-api and cms-admin stopped with `APP_ENV=development` renders every page from the mocks; BFF sign-in fails with its existing errors and the status card shows unreachable. Web unit tests need no cms-api.
- **WEB-9 `APP_ENV` environment** (user 2026-11-12, Q-WEM1, Q-WEM2). `APP_ENV` names the stack: `development`, `staging` or `production`; any other value or a missing key fails the build and the start. Next.js runs a built app with `NODE_ENV=production` on every stack, so `APP_ENV` is the one key that says which stack it is. It is given twice: at build (a GitHub Actions variable, a Docker build argument) and at runtime (the web Secret); the start fails when the runtime value differs from the build value. Today it decides the mock fallback only (WEB-5); every check that reads `NODE_ENV` (`APP_API_TOKEN` required, session secret length, the smoke opt-ins `ALLOW_TURNSTILE_TEST_SECRET` and `ALLOW_BFF_RATE_LIMIT_OVERRIDE`) stays as it is. Server only: never a `NEXT_PUBLIC_*` key. The dev stack sets `development`, the smoke stack `staging`, deploy config `staging` or `production` (patch note). A web image built in the GitHub Environment `production` refuses any `APP_ENV` but `production`: the image job fails before the build (Q-WEM6). With the start check above, a CI image therefore runs only with `APP_ENV=production` and never carries the mocks; a `staging` web image comes only from a local build (smoke stack, local registry).
- **WEB-10 One API error shape** (user 2026-11-12, Q-WEM5). Every API failure in web, server and browser, is one type, `WebApiError`, with `source` (`cms-api` REST, `cms-api` GraphQL, `bff`, `turnstile`, `client`), `errorCode` (from one closed list that keeps today's codes: server RESTful, GraphQL, BFF and the client failure kinds, plus the cms-api `errorCode` it carries), `statusCode` (when there is one), `operation` (GraphQL operation or BFF route), `retryable` and, for a rate limit, `retryAfterSeconds`. It never holds a token, a cookie, a request body or upstream text. The server RESTful, server GraphQL and client RESTful layers and every BFF route raise or return only this type; the BFF answer body stays `{ statusCode, errorCode, message }` (D21) for every refusal and unexpected error, and the client RESTful layer reads it back into `WebApiError`. One logger writes one line per failure (`source`, `errorCode`, `statusCode`, `operation`), the single hook a later error tracker plugs into. The UI branches on `errorCode` and `retryAfterSeconds`, never on the `source` or a message.

## Decisions

**D21 Web BFF and web hardening (added 2026-10-31, user request Q7; [ADR 0018](../../adr/0018-web-bff.md) holds design, error list, module map, file map; feature `web-bff-hardening`).** Q-BFF1..Q-BFF5 answered by the user 2026-10-31: Q-BFF1 yes (cms-api moves to `admin.domain.com/api`); Q-BFF2 the homepage shows only the service status view and the CV moves to `/cv`; Q-BFF3 Turnstile on both 2FA steps; Q-BFF4 the web login reuses the reviewer Turnstile keys; Q-BFF5 the web reviewer files, `/status` and `Graphql.client.ts` are deleted (the builder asks before each delete).

- **Topology.** The BFF is part of apps/web: Next.js Route Handlers under `/api/v1` (route files `app/api/v1/**/route.ts`), same Node server and origin. The path prefix lives once, in `BFF_BASE_PATH` (the web endpoint map); internal names keep the word `bff`. The retired prefix `/bff/v1/*` is not served: web's plain 404, no alias, no redirect (user 2026-11-06). cms-api also serves `/api/v1/*`, but only on the admin origin, so a request is told apart from a cms-api call by its origin, never by its path prefix. The browser calls only the web origin; no browser code knows a cms-api URL (`NEXT_PUBLIC_API_BASE_URL`, `DEV_API_PROXY_TARGET` retired). The BFF reaches cms-api only on `APP_API_URL` (cluster-local Service URL), never following redirects. Q-BFF1: Traefik serves no cms-api route on `domain.com`; cms-api's public route moves to `admin.domain.com/api` for cms-admin (same-origin, no cms-api code change); a NetworkPolicy lets only Traefik and web pods reach cms-api.
- **Endpoints** (§9 "Web BFF"): `GET /health`, `GET /session`, `POST /auth/login`, `POST /auth/two-factor/email-code`, `POST /auth/two-factor/verify`, `POST /auth/logout`, `GET /cv`; each with a fixed list of cms-api calls (ADR 0018 §2); no generic proxy, no GraphQL passthrough; nothing from the request reaches cms-api but the validated body fields and the forwarded client IP.
- **Session.** No token in the browser. `__Host-abyss_web_session` holds the sealed `{ refreshToken, accessToken, accessExpiresAt, rememberMe }`; `__Host-abyss_web_2fa` the sealed 2FA challenge for 300 s, which also carries `rememberMe` from `POST /api/v1/auth/login` (`rememberMe?`) to verify. Both `HttpOnly; Secure; SameSite=Strict; Path=/`, no `Domain`. `__Host-abyss_web_session` is a browser-session cookie (no `Max-Age`, no `Expires`) unless remembered, then `Max-Age` 30 days (D22), set again on each refresh (amended 2026-11-03, Q-RM7, §16 RM-6). Sealed with AES-256-GCM, key derived from `WEB_SESSION_SECRET` (required, ≥ 32 bytes in production, else start fails), cookie name as additional data; a cookie that does not open counts as absent and is cleared. Refresh when the access token has < 30 s left; concurrent refreshes of one token share one in-process call and its result for 10 s (D9 family revocation never fires on a race; single replica, like D16). Accounts with any permission other than `read` are signed out at cms-api and refused (`403 BFF_PRIVILEGED_ACCOUNT`) after login, after 2FA and on every session read. Sign-out calls cms-api logout and always clears both cookies.
- **Pipeline on every BFF route, in order:** allowed method only · state-changing routes need `Origin` exactly `WEB_ORIGIN` and `Sec-Fetch-Site` (when sent) `same-origin` · POST bodies `application/json` only, never CORS headers · body ≤ 8 KiB · per-IP fixed-window rate limit (`auth` 20 / 60 s, `read` 120 / 60 s, at most 10 000 keys) · Zod schema per body, unknown keys refused, lengths capped · Turnstile check where needed · upstream call with `API_TIMEOUT_MS`, forwarded client IP (D7), only the headers that call needs · answer with allowlisted fields, errors `{ statusCode, errorCode, message }` from the ADR 0018 §3 list, `Cache-Control: no-store` · log route and error code of refused requests, never bodies, tokens, codes, cookies, emails or passwords.
- **Human check.** Cloudflare Turnstile on the login form (`login`) and in the 2FA popup (`two-factor`: sending the email code and verifying, a fresh token each, Q-BFF3). The BFF verifies server-side (`siteverify` with `TURNSTILE_SECRET_KEY` in the web server env, `remoteip`, expected `action`, `hostname` = `TURNSTILE_EXPECTED_HOSTNAME` when set) before any cms-api call; failure `400 BFF_HUMAN_CHECK_FAILED`, siteverify unreachable `503 BFF_HUMAN_CHECK_UNAVAILABLE` (fail closed). `NEXT_PUBLIC_TURNSTILE_SITE_KEY` required at build. Dev, demo and smoke use Cloudflare's published always-pass test keys; the `action` comparison is skipped only when `TURNSTILE_SECRET_KEY` equals that published test secret (a named constant; that secret accepts every token anyway), and `success` and the hostname rule still apply (Q-WBH3, user 2026-11-05). **Production guard** (WBH-2-security#1, planner 2026-11-05, ADR 0018 §2.6): with `NODE_ENV=production` the web server refuses to start when `TURNSTILE_SECRET_KEY` is that test secret and `ALLOW_TURNSTILE_TEST_SECRET` is not exactly `smoke`, or when a real secret runs without `TURNSTILE_EXPECTED_HOSTNAME`; only the smoke stack sets the opt-in, deploy config never does. Outside production nothing changes. The widget script loads only while the login dialog is open.
- **Reviewer mode on web is removed**, not paused (ADR 0018 §5); Turnstile widget and hook move to `features/auth`. cms-api's reviewer module, cms-admin's Reviewer page and `REVIEWER_FEATURE_ENABLED` are unchanged (D2a).
- **Homepage and CV page (Q-BFF2, user 2026-10-31).** `/` shows only the service status view, like cms-admin's home: the "Service status" card polls `GET /api/v1/health` and shows only that path; it loads no CV data. The CV page moves to `/cv` (server render as today, refetch for a signed-in visitor through `GET /api/v1/cv`). A "CV" link in the site header, next to the account menu, leads to `/cv`; `/` itself stays status-only (Q-WBH1, user 2026-11-05). Always on; `/status` and `WEB_STATUS_PAGE_ENABLED` removed.
- **Web env** (server, runtime): adds `WEB_ORIGIN`, `WEB_SESSION_SECRET`, `TURNSTILE_SECRET_KEY`, `TURNSTILE_EXPECTED_HOSTNAME` (bare lower-case hostname; required in production unless the test secret runs with the opt-in), `ALLOW_TURNSTILE_TEST_SECRET` (optional, only `smoke`; any other value fails start), `BFF_AUTH_RATE_LIMIT_IP` and `ALLOW_BFF_RATE_LIMIT_OVERRIDE` (optional; raise the `auth` bucket limit on test stacks only, refused in production without the opt-in, ADR 0018 §2.7), `TRUST_PROXY_HOPS` (default 1), `CLIENT_IP_HEADER` (optional); removes `WEB_STATUS_PAGE_ENABLED`, `NEXT_PUBLIC_API_BASE_URL`, `DEV_API_PROXY_TARGET`. Invalid values fail start (instrumentation), as today. In the dev stack cms-admin reaches cms-api through a dev-only `/api` proxy of its Vite dev server (`DEV_API_PROXY_TARGET`, never in a build), so dev keeps the production topology (Q-WBH4, user 2026-11-05).
- **Build order with remember-me (planner 2026-11-05, Q-RM9).** web-bff-hardening builds the session without `rememberMe`: its sealed shapes have no such field, `__Host-abyss_web_session` is always a browser-session cookie and its login sends cms-api no `rememberMe`. Feature remember-me phase 2 (sign-in RM-6) adds the field and the remembered mode described under Session; a sealed session without it reads as `false`.
- **Note (2026-11-05):** the design ADR is [ADR 0018](../../adr/0018-web-bff.md); the ADR 0017 named on 2026-10-31 was never committed and the number now belongs to the cms-admin locale loader.
