# cms-api: spec

Part of the [project spec](../../../SPEC.md). App `cms-api`: [SPEC.md](SPEC.md) · [FLOW.md](FLOW.md) · [RULES.md](RULES.md). In these files a section without an `Applies to:` line covers every flow that touches this app.

## Behaviour

cms-api (NestJS 11 on Express) serves every API under `/api/v1`, except its health routes at the server root (API-3): REST for cms-admin and API tokens, and the read-only GraphQL API the web server reads. It owns the database (Prisma core tables in `public`, generated content tables in `content`), the access policy and field masking, sessions and tokens, and the security audit. Modules and their dependencies: [capability-map.md](../../global/reference/capability-map.md); endpoints: [api-contract.md](../../global/reference/api-contract.md).

## Requirements

The decisions below, plus the requirements of the flows that use cms-api (Docs table of the [project spec](../../../SPEC.md)). New app-wide requirements go here with ids `API-<n>`.

- **API-1 Request duration log** (user, 2026-11-07). cms-api writes one log line through the project logger (`AppLogger`, [logging module](../../modules/cms-api/logging.md)) for every request it answers: method, path, status and duration in whole milliseconds. The path is the request path only: no query string, and never headers, body or cookies. Level `info`; `warn` when the duration exceeds a named threshold constant. Requests to the health routes (`/health` and below, API-3) are not logged.
- **API-2 `NODE_ENV` values** (user, 2026-11-14, `DESIGN NODE_ENV enum for cms-api`). cms-api accepts exactly `development`, `staging` and `production`; any other value (`test` included), or none set where the default does not apply, fails the start (default `development`, as today). Every production-only behaviour (the D17 config guards, the D19 role warning, the `seed:account` opt-in, the mail and media provider refusals, GraphQL introspection off and suggestions stripped) runs only with `NODE_ENV=production`; `staging` behaves like `development` for all of them. The deployed staging environment sets `staging`; production sets `production`; the dev stack `development`; the cms-api test runner (unit and integration) `development`, overriding the `test` its runner sets by default; the smoke stack `production` (unchanged). A new value is added to the one list of node envs in the config module; a behaviour that should also cover staging is a new decision, never a change to what `production` means.
- **API-3 Health routes at the root** (user 2026-11-24, verbatim: "Chuyển tất cả health api về dạng `/health` cms-api, cms-admin"; in English: move every health API to the `/health` shape, cms-api and cms-admin; the same day the user kept all three paths `/health`, `/health/live` and `/health/ready`). Aligns cms-api with the web's own `/health` (public-site PS-8): the health routes are unversioned and sit at the server root, outside `/api/v1`. Q-HR1..Q-HR4 answered by the user 2026-11-24.
  - **Routes.** cms-api serves `GET /health`, `GET /health/live` and `GET /health/ready` at its root, outside the `/api/v1` prefix; they are the only cms-api routes outside it. `HEAD` on each answers the same status with no body. Each is owned by the cms-api `health` module; the paths are named once in that module and the prefix exception once in the app setup.
  - **Answers.** `/health/live` and `/health/ready` answer as today (`{ status }` only, never internals; `/health/ready` pings the database within 2 s and answers 503 `{"status":"error"}` when it fails). `/health` answers like `/health/live`: 200 `{"status":"ok"}` while the process runs, without a database call, so a paused database (`docs/deployments/database.md`) fails only `/health/ready` (Q-HR1, user 2026-11-24: same as `/health/live`).
  - **The old paths go.** `/api/v1/health/live` and `/api/v1/health/ready` are no longer served: cms-api's standard 404, no alias, no redirect (Q-HR2, user 2026-11-24: removed in this release; the probes change in the same deploy commit).
  - **Same pipeline.** The health routes keep the security headers (D17), the request id, the CORS rule (D14) and the error shape of every cms-api answer, tolerate a trailing slash like every route ([canonical-values.md](../../global/reference/canonical-values.md)), need no credentials and are not logged (API-1).
  - **Through the proxy** (Q-HR3, user 2026-11-24: cms-api owns `/health` on the admin host; no cms-admin uptime route for now). On `admin.<domain>` Traefik routes `/health` and below (whole path segment, like `/api`) to cms-api, ahead of the cms-admin catch-all; cms-admin's nginx gets no health route of its own and its pod probe stays `GET /`. On `<domain>` nothing changes: `/health` stays the web's own check (PS-8) and `/health/live` and `/health/ready` stay the web's 404, so cms-api is still never served on the web origin (D21).
  - **Callers move with it.** cms-admin's service status card reads `GET /health/live` on the cms-api origin (the origin of `VITE_API_BASE_URL`; the dev server forwards `/health` as it forwards `/api`); the web BFF `GET /api/v1/health` (unchanged, D21) reads cms-api's `/health/live` on the origin of `APP_API_URL`; neither adds an env key (Q-HR4, user 2026-11-24). The cms-api Kubernetes liveness and readiness probes move to `/health/live` and `/health/ready` on port 3000, and the admin-host route of Traefik is added; both are deploy repo changes, so the feature updates `docs/deployments/` (kubernetes, traefik, and the checks in release, database and backups) and adds `docs/apps/cms-api/patch-cms-api-<repo version>.md`, which says the new image and the new probe paths go out in the same deploy commit (a new pod with the old probes never becomes ready). The smoke and dev stacks (compose health check, readiness waits, CORS, security-header and routing checks), the e2e endpoint map, the route snapshot test, the endpoint references ([api-contract.md](../../global/reference/api-contract.md), [canonical-values.md](../../global/reference/canonical-values.md)), the module docs and the app READMEs follow the new paths.
  - **Check.** Through the proxy: `GET https://admin.<domain>/health`, `/health/live` and `/health/ready` answer 200 `{"status":"ok"}` from cms-api (D17 headers present); with the database stopped, `/health/ready` answers 503 while `/health` and `/health/live` stay 200; `/api/v1/health/live` answers cms-api's 404; on `<domain>`, `/health` is still the web's check and `/health/live` the web's 404; the cms-admin status card shows cms-api up and the web status card still works; the smoke stack goes healthy with the new compose check.
  - **Not in scope:** a health or uptime route served by cms-admin's nginx (Q-HR3); the web's `/health` and BFF `GET /api/v1/health` (PS-8, D21, unchanged); what the readiness check pings; any other route leaving `/api/v1`.

## Decisions

**D3 Field-level reads (C4).** Applied **when the query is built**: no `read` on a subject → `403` (not a masked row) · unreadable columns are never selected; the serializer emits the sentinel and `_maskedFields` · filter, sort or search on an unreadable field → `400 FIELD_NOT_READABLE` · every payload carrying record data uses the same serializer (list, detail, 409 conflict, bulk conflicts, audit metadata view, error details).

**D4 Write allowlist (C5).** Writable fields come from policy, per request. A masked field sent back with the sentinel is dropped silently; any other non-writable or unknown key → `400`. Client-sent `_maskedFields` is ignored.

**D5 API tokens (C6).** Effective permissions = token scope ∩ creator's **current** permissions, per request. A deactivated or deleted creator stops the token. Create, update and revoke only from a JWT session (never with a token); the subset check runs on create **and** update. Admins manage only tokens they created; the Owner manages all. Format `ak_live_` + 32 random bytes base64url, stored as SHA-256, raw value shown once. Expired once `expires_at <= now` (same rule at request authentication and in the list status). Expired = revoked: no update (`PATCH /api-tokens/:id` → `409`, so an expiry can never be moved forward to revive it); only a new token restores access (user decision 2026-10-25, CA1b security).

**D8 Credentials and OTP.** Passwords: Argon2id, min 12 characters. OTPs stored as HMAC-SHA256 with `OTP_PEPPER`, bound to `(account, purpose)`; purposes `INVITE_SET_PASSWORD`, `RESET_PASSWORD`, `LOGIN_2FA_EMAIL`. Unknown-email responses look like known ones (no enumeration). Password reset also needs a TOTP code when TOTP is on. Turning on 2FA needs the current password plus a valid first code. TOTP remembers the last used time step (no replay); its secret is encrypted with AES-256-GCM using `TOTP_ENC_KEY` and a key id for rotation.

**D9 Sessions and revocation.** JWT HS256, algorithm pinned; claims `sub`, `tv` (`accounts.token_version`), `pv` (`roles.policy_version`), `kid`. The guard compares claims with DB values through an in-process cache invalidated on every write in that process: immediate at one replica, bounded by a 5 s cache TTL at more. Refresh tokens rotate with `family_id`; reusing a rotated token revokes the family and bumps `token_version`. A password change or reset bumps `token_version`.

**D19 Database roles (added 2026-10-27, user decision; ADR 0012).** Production uses separate PostgreSQL roles:

- `abyss_migrator` owns the database and runs DDL, only in the init container (`deploy:migrate` = `db:migrate` + `content:migrate`) and the restore drill. `abyss_api` (cms-api runtime): `SELECT, INSERT, UPDATE, DELETE` on app tables of `public` and `content` (plus `USAGE` on schemas and sequences), only `SELECT` on `_prisma_migrations`, `content._migrations`, `content._content_types`; no DDL, no `TRUNCATE`, no temporary tables. `abyss_backup` only reads (`pg_read_all_data`). The superuser stays in the Postgres pod.
- One idempotent, self-checking script, `scripts/db/database-roles.sql`, sets roles and grants; default privileges cover later objects. Each workload gets only its own credential Secret; migration commands load only `DB_*` keys (`loadDatabaseConfig`), so the init container holds no app secret. The tier 3 smoke stack uses the same split.
- In production cms-api logs one boot warning (names only, no values) when its role is superuser, can `CREATE` in the database or the `public` / `content` schemas, or owns objects there, and still starts. Until the split is applied on an environment, its shared DDL-capable DB account is a user-accepted risk (ADR 0012 §8). Every environment starts from a fresh database (user answers Q-DB1, Q-DB2 "warn only", 2026-10-27).
- Production on a managed PostgreSQL service (amended 2026-10-27, user decision, ADR 0012 §9): the service's admin role = migrator and operator, `abyss_api` = API role, `abyss_backup` reads with explicit `SELECT`. Every connection (API, init container, backup, roles script) is a session-mode connection (the login name the service expects), never a transaction-mode pooler. Roles script in its managed-service mode (no ownership change, no `PUBLIC` revoke, all grants removed from the service's data API roles); the data API off. TLS via `DB_SSL_MODE` / `DB_SSL_ROOT_CERT_PATH` (default `disable` for local stacks; production: `verify-full` with the service's CA, TLS enforced by the server). A plan that pauses an idle database is accepted for launch. Postgres 17 is the target major for production, tests, smoke, dev and backup images (user answers Q-DB3..Q-DB7, 2026-10-27).
