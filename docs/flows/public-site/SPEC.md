# Public site: spec

Part of the [project spec](../../../SPEC.md). Flow `public-site`: [SPEC.md](SPEC.md) · [FLOW.md](FLOW.md) · [RULES.md](RULES.md).

## Behaviour

The public site (`domain.com`, Next.js) shows only the module status (the "Service status" card) on the homepage `/` and on `/status` (Q-PS5, user 2026-11-15) and each published CV on its own page `/cv/<documentId>`, which only a person given the link can open: no page, header, sitemap or public API answer lists it, and no crawler may crawl or index it (PS-5, user 2026-11-19). The Next server reads content anonymously over the read-only GraphQL API (D18) on `APP_API_URL`; the browser calls only the web BFF under `/api/v1` (D21). Sensitive fields stay masked for anonymous visitors through the `public` role's field profile (D2 mechanism, [reviewer](../reviewer/RULES.md)). The full GraphQL decision is D18 in Decisions below.

Endpoints: [api-contract.md](../../global/reference/api-contract.md) rows "GraphQL (D18)" and "Web BFF". Web rules: [apps/web/RULES.md](../../apps/web/RULES.md) "Web rules".

Each part fetches its own data, within the D18 limits (5 root fields, depth 8, 500 field nodes): a page runs its own query, and a part shown on several pages (the header, the sign-in dialog) runs its own query in its own server component, through server GraphQL with `APP_API_TOKEN` (WEB-1, WEB-2). No query bundles the text of several parts, and no part fails because another part's query failed. Each answer is cached on its own (WEB-4); a page render runs the header, sign-in and page queries, in parallel.

The web does not read `requiresRole` (user 2026-11-19, feature `header-nav`: "skip the requiresRole field, it comes later"): the query selects it on neither level, and every `navs` entry and every `subNavs` entry with a title and a link the web's safe-link check accepts (a `navs` entry with sub navs needs only a title) shows to every visitor, signed in or not. The field stays stored in `header` with its options `public`, `owner`, `admin`, `editor`, unread until a later feature brings role-based display back (WEB-7). An entry's `subNavs` show as its sub list, in stored order, opened by pointer hover, keyboard focus and a tap on a touch screen, and closed by Escape; on a touch screen the first tap on an entry with sub navs opens its list and a second tap follows its link; an entry with sub navs and no link shows as a label that opens the list (Q-HN2). This is the header at the `md` width and wider; narrower, the entries move into the mobile nav drawer (PS-6). No nav title, link or app name is written in web source: all come from `header`, the last-resort app name of WEB-3 aside. When it fails, the header shows the last-resort app name and no nav or account menu (WEB-3).

When it fails, the account menu shows no sign-in button, no "signed in as" line and no sign-out failure text; the nav, the CV link and a signed-in visitor's sign-out button stay (Q-PS1b, Q-PS4).

  - `ModuleStatus` (the module status, owned by `features/status`, rendered by `PageHome` on `/` and `PageStatus` on `/status`; changed 2026-11-15, replaces `StatusPage`): `statusText` (alias of `moduleStatus`: title and description, card texts, states, error hint, check again). The health data stays on REST through `GET /api/v1/health` (D21). Both pages show the same module and load no CV data (criterion 25).
  - `PageCv` (`/cv/<documentId>`; changed 2026-11-15, replaces `CvPage`; split 2026-11-16, Q-PS2e; moved from `/cv` 2026-11-19, PS-5): three content queries, each its own GraphQL operation, run in parallel, so one that fails never touches the others: `PageCvA` reads `pageCvA(documentId: <documentId of the URL>)` on `page-cv-a` (published only; `isMain` is no longer read, Q-CL4); `Profile` reads `profile` (the single type, the contact card shared by every CV); `CvCommonText` reads `cvCommonText` (the labels shared by every CV and the no-CV-live text, PS-3). Their mock keys are `page-cv-a`, `profile` and `cv-common-text` (WEB-5, Q-PS2f). `PageCv` shows the CV's name, position, summary, skills, experiences with their roles, projects, educations, languages and references (added 2026-11-19, user), and the profile's name, avatar, address, phone, email, LinkedIn and GitHub as the contact card; a masked value shows the masked text (Q5); the page title is `<name> - <position>`.

It lives with `PageCv` (web RULES "Page layout" 6).

The query documents select them under the aliases `signInText` and `statusText`.
  - Text field names follow the current `COPY` keys (full list: `DESIGN web-content-api`); English only (Q-WCA11). The committed query documents are the contract the user builds cms-api from; types or fields not served yet fall back to the mocks where WEB-5 allows.
- **PS-2 States** (changed 2026-11-15, Q-PS2b; changed 2026-11-16, Q-PS2a, Q-WEM3, Q-PS2c; changed 2026-11-19, PS-5). The CV data comes from `page-cv-a` alone; `cvCommonText` and `profile` only dress it. `/cv/<documentId>` never answers 500 for its content (Q-PS2c). `PageCv` decides in this order:
  1. A `documentId` that is not a UUID: the not-found page, HTTP 404, with no cms-api call.
  2. A failed read gets its mock where the mock fallback is on (development and staging, WEB-5), for each of the three queries alone; a single type that answers null too. `pageCvA` answering null is never mocked (Q-PS2f).
  3. `pageCvA` answers null: no published `page-cv-a` has that `documentId` (unknown, never published, unpublished or deleted). The not-found page, HTTP 404, the same answer as for a malformed id (PS-5).
  4. The `pageCvA` read failed and no mock filled it (the mock fallback is off: production). The page shows the **no-CV-live state**: HTTP 200, the site header, `cvCommonText.noCvText` (sanitized richtext) or, when `cvCommonText` cannot load, the last-resort no-CV-live text (WEB-3); no CV, no contact card, the app default title. The failed read is logged once (WEB-10); a null answer is not an error.
  5. Otherwise the CV. Where the mock fallback is off, a missing `cvCommonText` shows the CV without labels (no section titles, contact labels or refetch-failed text; the page never fails for it), and a missing `profile` shows the CV without the contact card.

  A label the page shows that `cv-common-text` has no field for is left out, as when `cvCommonText` is missing (Q-PS2d). A signed-in visitor's refetch that fails keeps the server-rendered CV and shows the refetch-failed text, when there is one. The error page always, and the not-found page when `notFoundText` cannot load, use the last-resort set (WEB-3). A failed `ModuleStatus` query never hides the status card, which shows the last-resort card words and loads no CV data (criterion 25).

- **PS-4 Crawler files** (user 2026-11-16, Q-PS8..Q-PS14). The public site serves three files at its root, each with HTTP 200 and its own content type, never the not-found page. None calls cms-api, so none falls back to a mock (WEB-5).
  - `/robots.txt` (Q-PS13): where `APP_ENV` is `production` (WEB-9), `User-agent: *`, `Allow: /`, `Disallow: /api/`, `Disallow: /cv` (added 2026-11-19, PS-5; the rule covers `/cv` and every `/cv/<documentId>`); on any other stack `User-agent: *`, `Disallow: /`, so a development or staging site is never indexed. Always a `Sitemap:` line with the absolute URL of `/sitemap.xml`. Next.js writes the field name as `User-Agent:`; accepted, as field names are read case-insensitively (RFC 9309, Q-PS15).
  - `/sitemap.xml`: the public pages `/` and `/status` only (Q-PS10); no `/cv` path is ever listed (PS-5). No sign-in step, BFF route (`/api/...`), not-found or error page is ever listed. The paths are one static list in web config: no cms-api call and no `lastmod` (Q-PS11); a new public page in the sitemap is one entry in that list. URLs are absolute on `WEB_ORIGIN`, no new env key (Q-PS9).
  - `/favicon.ico`: a simple letter mark of the app name in palette A, designed by the planner (`DESIGN favicon`) and built as a static asset (Q-PS12).
  - Cache and CSP (Q-PS14): `robots.txt` and `sitemap.xml` are built per request (they read the runtime `WEB_ORIGIN` and `APP_ENV`) and answer `Cache-Control: public, max-age=3600`; `favicon.ico` keeps the Next.js static file caching. All three are skipped by the proxy matcher, so they carry no per-request nonce CSP, and keep the static security headers of `next.config.ts` (D17). The matcher change is checked on the full stack (tier 3).
  - The admin host (`admin.<domain>`, cms-admin) serves its own `/robots.txt` with `User-agent: *`, `Disallow: /` on every stack (Q-PS13).
- **PS-5 Link-only CV page** (user 2026-11-19, feature `cv-private-link`, verbatim: "cv page hiện tại sẽ có link `/cv/[documentId]` SSR - đảm bảo chỉ ai có link mới vào được, không scan, không craw ra được, không cho google hay crawler quét hay index luôn"; in English: the current CV page gets the link `/cv/[documentId]`, server-rendered; only a person who has the link gets in; no scanning, no crawling, no Google or other crawler may crawl or index it).
  - **Route.** Each published `page-cv-a` document is the server-rendered page `/cv/<documentId>`, its cms-api `documentId` (a random UUID v4, 122 random bits, so it cannot be guessed). `/cv` with no id is not served: the not-found page, HTTP 404 (Q-CL1). States: PS-2.
  - **Nothing hands out the id.** No web page, header entry built into the code, sitemap, crawler file or BFF answer lists a `page-cv-a` document or its `documentId`; the only way in is a link the owner shares. `page-cv-a` is a link-only type (CM-13), so no actor that only reads (anonymous, `guest`, `reviewer`, the web's `APP_API_TOKEN`, a signed-in web visitor) can list it over REST or GraphQL; the web reads it by id only. Which links the owner puts in the `header` content is the owner's choice; the smoke seed and the web mocks hold no `/cv` nav entry.
  - **One answer for every miss.** A malformed, unknown, unpublished or deleted id gets the same not-found page with HTTP 404 and the same headers; nothing in the body, the headers or the BFF error tells them apart. The BFF refetch `GET /api/v1/cv/{documentId}` answers `404 BFF_NOT_FOUND` (a new BFF error code) for all of them, after the session check (Q-CL2).
  - **No crawling, no index, no shared cache.** Every response under `/cv` (the CV, the no-CV-live state, the not-found answer) carries the header `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` and the robots meta tag with the same words, and `Cache-Control: private, no-store`. The production `robots.txt` disallows `/cv` (PS-4, Q-CL7); no other stack is crawled at all (PS-4). The sitemap never lists a `/cv` path (PS-4).
  - **The link does not leak from the page.** The site's `Referrer-Policy: strict-origin-when-cross-origin` (D17) stays, so a link the CV opens to another site sends only the origin, never the `/cv/<documentId>` path; outbound links keep `rel="noopener noreferrer"`. A logged failure names the operation or route pattern (`PageCvA`, `/api/v1/cv/[documentId]`), never the `documentId` (WEB-10).
  - **No scanning.** With no list for read-only actors and 122 random bits per id, guessing is the only way to find a CV; the page gets no rate limit of its own (Q-CL3).
  - **Signed-in visitor.** A signed-in visitor's view reads the same CV again through `GET /api/v1/cv/{documentId}` with the visitor's token (D21), by id only; `GET /api/v1/cv` without an id is not served (404).
  - **Not in scope:** a "copy public link" action in cms-admin (the `documentId` is in the cms-admin edit URL; Q-CL5); expiring or per-recipient links; role-based display of the header (PS-1 `SiteHeader`).
- **PS-6 Mobile nav drawer** (user 2026-11-19, feature `header-mobile-drawer`, verbatim: "nên làm side-menu ở mobild cho gọn"; in English: make a side menu on mobile to keep the header compact; Q-HN3..Q-HN6).
  - **Where.** Below the `md` width (768 px, the width below which cms-admin shows its mobile menu) the header bar holds the app name, the account menu (PS-1 `SignIn`, as it is, Q-HN6) and a menu button; the nav entries are not in the bar. At `md` and wider the header is unchanged (PS-1 `SiteHeader`, Q-HN2), touch screens of that width included.
  - **Menu button.** An icon-only button (a three-line menu icon) at the end of the bar, named by the built-in word "Open menu" (WEB-3, Q-HN4); it says that it opens a dialog and whether it is open. It shows only when the header loaded and at least one entry passes the PS-1 show rule; when `SiteHeader` fails the bar has no nav and no menu button (WEB-3).
  - **Drawer.** Hidden until the button is pressed; then a side panel slides in from the right edge (the side of the button) over a dimmed backdrop. It is a modal dialog: focus moves into it, stays in it while it is open and returns to the menu button when it closes; the page behind it does not scroll. Its title is the app name of `header` (the WEB-3 last-resort app name never applies: no header, no drawer); an icon-only close button named by the built-in word "Close menu" (WEB-3, Q-HN4).
  - **Content.** The same entries as the bar, by the same show rule and safe-link check (PS-1 `SiteHeader`), in stored order, as one vertical list with tighter spacing than the bar, each row a tap target at least 44 px high. An entry's shown sub entries are always listed, indented, under it (Q-HN5): no hover, no tap to open, no second tap in the drawer. An entry with sub entries and no safe link is a plain group heading, neither a link nor a button. A link to another site keeps `rel="noopener noreferrer"`.
  - **Closing.** The drawer closes on a tap on any link in it (a link to the current page too), the close button, Escape, a tap on the backdrop, a route change, and the window growing to the `md` width or wider while it is open.
  - **Look.** Styles and motion from the existing design tokens (D23); no slide motion under `prefers-reduced-motion`; hidden in print with the header.
  - **No new data.** The drawer reads the `SiteHeader` answer the header already loaded: no new query, content field, migration or BFF call.
- **PS-7 Print the CV to PDF** (user 2026-11-23, feature `cv-print`, verbatim: "Thêm chức năng in ra pdf đảm bảo kết quả giống trong web `public/*.pdf`"; in English: add a print-to-PDF function whose result matches the PDF in the web `public/` folder; Q-CP1..Q-CP6 answered by the user 2026-11-23).
  - **Where.** The CV page `/cv/<documentId>` only, in the CV state (PS-2 item 5); never the no-CV-live state, a not-found page, `/` or `/status` (Q-CP1). While a signed-in visitor's refetch loads, the page shows no CV and so no button.
  - **Button.** One secondary button (ui-direction: styled by function) labelled by `cvCommonText.print`, a new optional text field of `cv-common-text` (PS-3; Q-CP4). No label, no button, as for every CV label (Q-PS2d). Pressing it opens the browser's print dialog (`window.print()`), where the visitor prints or picks "Save as PDF". The print look is the page's print stylesheet: no new dependency, no PDF built on the server, no BFF call, no new query (the label is one more field of the `CvCommonText` selection) (Q-CP3).
  - **Screen layout unchanged** (Q-CP2). The button moves no CV block and adds no row: it sits in the top-right corner of the CV header band, over the band, on every width, and the band keeps it clear of the name (Q-CP5). Everything else on screen stays as it is.
  - **The print matches the reference.** The reference is `apps/web/public/Middle-Frontend-Developer_HungNguyenHuy_CV.pdf` (planner 2026-11-23, assumption: the user named no file; this one was printed from the current `/cv/<documentId>` page by Chrome 152, the other, `CV_NguyenHuyHung_Frontend_Developer.pdf`, from the retired `/cv` page by Chrome 149). The print of a CV has: A4 portrait; the header band from the top edge of the first page, edge to edge, its tint printed; the text inside 10 mm side margins and 12 mm top and bottom margins on every later page; the tints, chips and rules as on screen and every text readable in black and white; links printed as their text with no underline; a block (company bar, role with its period, project panel, section heading with the first lines under it, skill group, reference) never split across two pages when it fits on one. Not printed: the site header, the mobile nav, the print button and any other control. The browser adds no header or footer (no URL, date, title or page number): the print stylesheet turns them off, so the visitor never has to untick a dialog option. For the same CV data, Chromium desktop browsers (Chrome, Edge; the browser of the reference) give the reference's page count and page breaks; Firefox and Safari print the same layout as far as they support the print stylesheet (assumption).
  - **The link does not leak (PS-5).** No printed page carries the page URL or the `documentId`; the PDF title, which the browser also offers as the file name, is the page title `<name> - <position>` (PS-1 `PageCv`), never the `documentId` (the reference's own title holds one; it came from an earlier build and is not copied).
  - **Only what the screen shows.** The print holds exactly the CV the visitor sees: masked values stay masked for an anonymous visitor (Q5); a signed-in visitor prints the data of their refetch.
  - **The static PDFs stay.** The files in `apps/web/public/*.pdf` are not built, replaced or deleted by this requirement; the printed PDF is the visitor's own file, next to them (assumption). They are not committed under `apps/web/public/`, which Next.js serves at the site root; the reference is kept outside the repo or under `docs/` (assumption, Q-CP6); deleting them from `apps/web/public/` is asked at the feature close.

## Decisions

**D18 GraphQL read API.** Details and schema contract: `docs/modules/graphql.md`, ADR 0003. In v1 by user decision; Q-G1..Q-G7 answered by the user 2026-10-21 as recommended (§14).

- `POST /api/v1/graphql`, queries and document reads only (no mutations, subscriptions, batching, GET or persisted queries). cms-admin stays on REST.
- Schema generated by a pure function from the content definitions: object type per content type and component, offset paging `page`/`pageSize` + `meta { page, pageSize, total }`, typed filter inputs with the REST operator sets and limits, sort ≤ 3 keys. Fails on any name clash; the printed SDL is committed (`content/schema.graphql`) and checked.
- **Authz is the REST read path, not a copy:** `DocumentAuthGuard` (anonymous, JWT, API token per D5), then root resolvers call `DocumentsQueryService` unchanged (read + draft rule, row conditions, projection, `QueryGuard` → `FIELD_NOT_READABLE`, `RecordSerializer`, media embed). Nested fields only read the serialized record; no other data path (architecture test). An unreadable content type fails validation exactly like an unknown field (hidden = unknown).
- **Limits** (named constants): body 32 KiB, 2 000 parser tokens, depth 8, 5 root fields per operation (aliases count), 500 field nodes; the anonymous document read throttle counts each request once. No weighted cost (DB work per root field is fixed).
- **Production:** introspection off, "Did you mean" suggestions stripped; no playground in any environment. Responses `Cache-Control: no-store`.
- **Errors:** `{ data?, errors: [{ message, path?, locations?, extensions: { code, details?, requestId } }] }`; `code` reuses REST codes plus `GRAPHQL_PARSE_FAILED`, `GRAPHQL_VALIDATION_FAILED`, `GRAPHQL_LIMIT_EXCEEDED`; HTTP 400 for parse/validation/limit errors, 200 once executed; failures before GraphQL (401, 413, 415, 429) keep the REST error shape. Never echo submitted values or log variables.
