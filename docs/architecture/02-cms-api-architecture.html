cms-api architecture

How the API is organised: layers inside modules, the module graph, the request pipeline, errors and transactions.

Style: modular monolith + clean architecture

One NestJS process. Business features are modules under src/modules/; each module is split into layers (ADR 0006). Dependencies point inward: HTTP, CLI and jobs call use cases; use cases depend on domain rules and on ports (interfaces + DI tokens); adapters implement those ports with Prisma, Kysely or SDKs; the module file binds ports to adapters. Modules talk to each other only through their index.ts facade and only along the allowed edges.

Layers inside one module. Dashed: adapters implement the ports declared in application/.

Error model

Domain and application code throw DomainError (common/errors/Domain.errors.ts) with a kind and an errorCode; they never throw Nest HTTP exceptions. HttpExceptionFilter maps every error to one body: { statusCode, errorCode, message, details?, requestId }. GraphQL keeps its own envelope but reuses the same codes.

Transactions, audit and afterCommit

Two runners behind one port: CORE_TRANSACTION_RUNNER (Prisma, schema public) and CONTENT_TRANSACTION_RUNNER (Kysely, schema content). Security audit rows are written with the same unit of work, so an action and its audit row commit together (D15). Side effects that must not run on rollback (cache invalidation, activity tracking) are registered with afterCommit.

sequenceDiagram
  participant UC as Use case
  participant TR as TransactionRunner port
  participant AD as Prisma or Kysely runner
  participant DB as PostgreSQL
  participant AC as afterCommit callbacks
  UC->>TR: run(work)
  TR->>AD: begin transaction
  AD->>DB: BEGIN
  AD->>UC: work(unit of work)
  UC->>AD: repository calls with the same unit
  UC->>AD: audit.record(unit, row) in the same transaction
  UC->>AC: unit.afterCommit(cache invalidation, activity)
  AD->>DB: COMMIT
  AD->>AC: run callbacks only after commit
  AD-->>UC: result
