# ADR 0003: Read-only GraphQL over the existing document read path

- Status: proposed (planner, 2026-10-21; GraphQL itself decided by the user, details pending Q-G1..Q-G7)
- Date: 2026-10-21

## Context

The user moved GraphQL from the v2 backlog into v1: cms-api gets GraphQL with
filter and pagination, and apps/web (Next.js 16) fetches its server data
through it instead of REST. Content types are defined at runtime by JSON
schemas, field-level permissions are applied when the query is built (D3),
and every record payload must go through one serializer. A second read path
with its own SQL or masking would split the security model.

## Decision

- One endpoint `POST /api/v1/graphql`, queries only, document reads only.
- The schema is generated by a pure function from the content definitions;
  object types per content type and component, offset pagination, typed
  filter inputs with the REST operator sets.
- Root resolvers call `DocumentsQueryService` unchanged; nested fields only
  read the serialized record. No other data path (architecture test).
- Authz reuses `DocumentAuthGuard`, the policy evaluator, row filters,
  `QueryGuard` and `RecordSerializer`. A content type the actor cannot read
  fails validation exactly like an unknown field (hidden = unknown).
- Limits: body size, parser tokens, depth, root fields (incl. aliases), total
  field nodes; no weighted cost (DB work per root field is fixed).
- Production: introspection off, suggestions stripped, no playground; a
  committed SDL replaces introspection for tooling.
- In-house HTTP handler on graphql-js inside the Nest pipeline.

Details: [docs/modules/graphql.md](../modules/graphql.md).

Alternatives rejected:

- `@nestjs/graphql` + Apollo: code-first decorators need static classes;
  runtime-defined types would need a schema-first workaround, plus heavy deps
  and a landing page we would disable.
- Generic `document(type: String!): JSON`: no typed filters or tooling; the
  web gets no contract check.
- Per-actor schemas: correct visibility but cache keys per role, token and
  policy version; the validation rule gives the same hidden = unknown result.
- Cursor pagination: REST and the admin already use offset (SPEC Q10).

## Consequences

- Any change to document read rules lands once, in the query service, and
  both REST and GraphQL get it.
- Adding a content type changes the schema; `graphql:print-schema --check`
  in tests/CI catches a stale SDL and name clashes before deploy.
- Field-level loading by selection is not done; if added later, a cost rule
  is required.
