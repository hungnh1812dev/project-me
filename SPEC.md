## How this spec is organised

This file is the entry point of the spec: what the project is, its objective and its scope. Everything else lives in its own file, by scope and by kind:

| Scope | Where | Holds |
|---|---|---|
| flow | `docs/flows/<flow>/` | One business flow: `SPEC.md` (behaviour, requirements, acceptance, decisions), `FLOW.md` (actors, steps, sequence diagram, the modules taking part), `RULES.md` (rules of this flow only) |
| app | `docs/apps/<cms-api, cms-admin, web>/` | What every flow of one app shares: `SPEC.md` (app-wide requirements and decisions), `FLOW.md` (processes such as the request pipeline), `RULES.md` (rules every flow of the app keeps) |
| global | `docs/global/` | What every flow shares, or several flows across apps: `RULES.md`, `FLOW.md`, `DECISIONS.md` (cross-app decisions and the index of every `D` id), `ACCEPTANCE.md` (success criteria, testing), `reference/` (definitions and values only) |
| modules | `docs/modules/`, index [docs/modules/MODULES.md](docs/modules/MODULES.md) | Where the code lives: each module's doc, doc status and flows |

A section of a global or app `RULES.md` / `FLOW.md` that covers only some flows starts with an `Applies to:` line naming them; no line means all flows. Each fact is written once, in the doc that owns it, and referred to elsewhere by id. Decisions (`D..`, decided questions) are records kept as written; the rules that follow from them are in the `RULES.md` files.

Where new work goes: [docs/global/FLOW.md](docs/global/FLOW.md) "Where a change goes". This file changes only for the project description, objective and scope; the [Docs](#docs) table is generated by `.claude/bin/module-index`, and `--check` fails when it is stale.

## 0. Assumptions (correct these before implementation starts)

1. One owner (the portfolio author) plus a few invited editors/admins. Not multi-tenant.
2. One Kubernetes cluster per environment with Traefik, **one replica per app in v1**. In-memory caches only where marked, each saying what changes at more than one replica.
3. PostgreSQL 17 on a managed PostgreSQL service, via a session-mode connection with TLS (amended 2026-10-27, user decision, ADR 0012 §9, D19); the in-cluster StatefulSet with a PVC stays the documented self-managed alternative. The separate deploy repo owns backups; this repo documents what they must cover.
4. Public self-registration is **off**; accounts are created by invitation.
5. v1 scope is cut down (§2). To v2: GraphQL mutations/subscriptions (a read-only GraphQL query API is in v1, D18), Group 2 runtime DDL, reviewer write sandbox, S3, Yup.
6. Domains: `domain.com` (web + API under `/api/v1`) and `admin.domain.com` (cms-admin).

## 1. Objective

Build a headless CMS that is:

1. **Content hub:** the owner manages and publishes CV/portfolio content defined by JSON schemas (root + up to 3 nested component levels), served over REST, plus a read-only GraphQL query API for document reads (D18).
2. **Technical showcase:** ERP-grade concerns that hold up under attack: hybrid RBAC + field-level permissions with `***` masking, draft/publish with optimistic concurrency and diff/merge, an always-on security audit, and a safe "Login as Reviewer" experience.

Actors (threat model):

| Actor | How they get in | Can do (v1) |
|---|---|---|
| Anonymous | none | Read **published** content through the `public` role's field profile |
| Reviewer | Self-service session (Turnstile + rate limit), 24h, when Owner enables it and the deploy switch `REVIEWER_FEATURE_ENABLED` is `true` (D2a) | Read published content through the `reviewer` role's field profile, browse preset media. **No writes, no drafts.** |
| Editor (rank 30) | Invitation | Permissions granted to their role |
| Admin (rank 40) | Invitation | Manage accounts/roles/tokens **strictly below** rank 40, plus their role's content permissions |
| Owner (rank 100) | One-time setup page with the setup token while no owner exists, or the `owner:bootstrap` CLI (D1) | Everything |
| API token | Created by an Admin/Owner session | ≤ creator's **current** permissions, content endpoints only |

Success = every item in §12 has a passing automated test.
