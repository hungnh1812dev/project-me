# Roadmap

The CMS Admin re-implementation ships in big phases. Each big phase gets its own spec, plan and tasks, and starts only after the previous one is merged. This page carries the roadmap and the open questions forward once the working spec is removed. It is cross-cutting: it owns no source files.

### Deferred questions

Resolve each one before the named phase starts.

1. **Phase 7:** does "internationalization" mean translating the admin UI (for example with `react-i18next` and a language switcher), localized content, or both? The backend currently has **no** locale support (no `locale` parameter and no locales module), so localized content would need backend work first.
2. **Phase 3 (closed, sharing reversed in Phase 6):** which styling stack should the design system use, and should it be shared through `@repo/ui`? **Decision:** Tailwind CSS v4 + shadcn/ui in the Base UI flavour + `lucide-react`, vendored app-locally in `apps/cms-admin/src/components/ui`. `@repo/ui` stays empty until a second app needs the primitives. **Reversed in Phase 6:** the stack is unchanged, but the primitives now live in `@repo/ui` so `apps/frontend` can reuse them (see question 3). See [Design system](./design-system.md).
3. **Phase 6, shared package (closed):** what is the package called, how is Tailwind v4 shared with `apps/frontend`, and do the form components that depend on the admin's data layer stay in `cms-admin`? **Decision:** D1, the existing `@repo/ui`, shipped as source and compiled by each app (Vite in cms-admin, `transpilePackages` in frontend). D2, one shared `@repo/ui/styles/theme.css` (tokens, dark variant, `@theme inline`, focus and reduced-motion rules) that each app imports, plus an `@source` for the package; fonts and the rich-text styles stay per app. D3, only generic components move; `SchemaForm`, `SchemaField`, `PermissionTree` and `fields/` (including `MediaField` and `MediaPickerDialog`) stay in cms-admin. D4, frontend gets the wiring only, with no visible page change. See [Design system](./design-system.md).
4. **Phase 6, pagination (closed):** is 10 rows per page done client-side over the full list, or does the backend gain paging first, and should the page size stay changeable? **Decision:** D5, client-side over the full list each endpoint returns; the backend is unchanged. D6, a "Rows per page" select of 10/20/50/100, default 10, with `page` and `size` in the URL (left out at their defaults), as in the collection list. D7, Permissions page by permission rows, not by resource groups. D8, `MediaPickerDialog` is not paged. See [Settings foundation](./settings-foundation.md).
5. **Phase 6, palette (closed):** is there a reference brand colour, and does the refresh replace the indigo accent or add a second one? **Decision:** D9, a violet primary replaces indigo (violet-600 `#7c3aed` light, violet-400 `#a78bfa` dark), and an orange highlight is added (orange-700 `#c2410c` light, orange-400 `#fb923c` dark), used only for the active menu item, the current page, a badge variant and the UI kit swatches. The slate neutrals stay. D10, the `MediaField` preview uses the full `url` through `safeImageSrc`, and its icon buttons get tooltips. See [Design system](./design-system.md#tokens-and-palette). **Superseded by the luxury restyle:** the primary is metallic gold `#D4AF37` with a deep-gold `primary-ink` (`#7A5C14` / `#E0C068`), neutrals are warm stone, and `highlight` became deep gold so it doesn't clash with the gold primary.
6. **Deployment (closed):** should the `cms-admin` Dockerfile take a `VITE_API_URL` build arg, and should the config repo pass it? **Decision:** yes, a build arg of the `builder` stage, set in CI from the GitHub Environment variable `VITE_API_URL` (empty keeps the relative `/api/v1`) and checked in the built bundle by `.github/scripts/bundle-check.sh`. Prod needs it because nginx does not proxy `/api`. See [CSP and headers](./csp-and-headers.md) and [Testing and config](./testing-and-config.md).

### Known gaps carried over from Phase 1

- `PUT /users/:id` stores passwords unhashed on the backend, so the admin offers no password change until that is fixed.
- The profile page is read-only; profile editing moves to Phase 4 (done: name editing only, see _Known gaps from Phase 4_).
- Cross-tab session sync and health keep-alive pings are not implemented.

### Known gaps from Phase 2

- The manual smoke against the real backend on :8080 has not run: no `super_admin` credentials were available on 2026-10-01. Phase 2 moves to DONE once it runs and its result is recorded in [Content data](./content-data.md).
- The seeded `editor` role has no `content_type:read`, so no schema loads for an editor until that permission is granted. This is a backend seeding gap, not fixed in the admin.

### Known gaps from Phase 3

- The admin home welcome card has a capped width and is centred, while other cards inside the shell are full width.

### Known gaps from Phase 4

- The manual smoke against the real backend on :8080 has not run: no `super_admin` credentials were available on 2026-10-02 (D9). The settings contract is checked only against the legacy docs and the e2e mocks. Phase 4 moves to DONE once the smoke runs and its result is recorded in [Settings foundation](./settings-foundation.md#manual-smoke-against-8080-d9).
- `expiresIn: "1m"` is labelled "1 month" but has not been checked against the backend (D6). The smoke should create a token with it and compare `expiresAt` with the creation time. If `1m` means one minute, relabel it.
- The Roles page adds no client-side level-hierarchy rule for creating, editing or deleting roles (D4). It mirrors the backend contract (level 0 to 100 only), so an actor can create or edit a role above their own level if the backend allows it.
- `PUT /users/:id` still stores passwords unhashed on the backend, so the profile page edits the name only (D8).
- The pure-module 90% branch bar of AC-44 is met (97% or more) but checked by reading the coverage report, not enforced by a per-file threshold.

### Known gaps from Phase 5

- The manual smoke against the real backend on :8080 has not run: it is pending (2026-10-03, no `super_admin` credentials) (D9). The field value shapes, the `MediaAsset` value, the richtext HTML, the wording of 400 messages, the status transitions and the date filter format are checked only against the legacy docs and the e2e mock. Phase 5 moves to DONE once the smoke runs and its result is recorded in [Document editor](./document-editor.md#manual-smoke-against-8080-d9).
- **Richtext markup loss (D2).** Markup the editor does not support (images, raw HTML, other tags) is removed on save. The field warns before that happens, but the content is still lost.
- **Global columns (D6).** The column chooser saves the type's `listFields` (C3), so it changes the list for everyone; there is no per-viewer column choice.
- The seeded `editor` role still has no `content_type:read` (the Phase 2 gap), so an editor sees no content types until the backend seeding is fixed.
- There is no Status filter until the backend is confirmed to accept one (D7), and bulk create (D9, JSON import) has no UI (D5).
- `react-day-picker` 10.0.2, with the vendored `calendar.tsx` and `popover.tsx`, was approved by the user after the Phase 5 spec was written. AC-40 lists only `react-hook-form` and the four `@tiptap/*` packages, so this approval is the record for the extra dependency. `date-fns` was not added.
- The 90% branch bar on the seven pure content modules is met (93% or more) but read from the coverage report, not enforced by a per-file threshold.

### Known gaps from Phase 6

- **Collection list wire default (AC-20, decision).** The list's own default is `DEFAULT_LIST_SIZE = 10` in `listState.ts`. `LIST_DEFAULTS.size` stays 20, because it mirrors the backend's default and decides which `size` is left off the request, so the default list sends `size=10`. AC-20 was reworded with the user's approval to require this behaviour rather than a change to the constant.
- ~~The `destructive` badge fails axe colour contrast in the light theme.~~ **Closed by the luxury restyle (AC-9):** `destructive` is now `#B91C1C` (5.9:1 as text on its 10% tint), the badge passes axe in both themes and is back in the UI kit's Badge section.
- `GatedMenuItem` has no unit test (0% coverage); it had none before the move to `@repo/ui` either. The package's 70% gate on `src/form/**` is met as a whole.
- The Phase 6 security audit passed with no findings at any severity.
- `apps/frontend` is wired to `@repo/ui` only (D4). It renders no package component yet, has no Playwright tests, and its dark mode is still media-query based rather than the `.dark` switch.
- The settings lists page on the client over the full list each endpoint returns (D5). Very large lists still load in full; backend paging would need a contract change.
- The Phase 4 and Phase 5 manual smokes against :8080 are still pending; Phase 6 did not run them.

### Known gaps from the luxury restyle

- Chromium only: replacing a selection that spans several `.cm-line`s makes its native contenteditable code insert one inline-styled span, which `style-src-attr` blocks (one report, no source file). The editor stays styled and works; `e2e/csp.spec.ts` tolerates at most that one report on the `csp` project and fails on anything else, or on the same report in Firefox or WebKit. See [CSP and headers](./csp-and-headers.md#json-editor-under-the-csp).
- Browsers older than Chrome 73, Firefox 101 or Safari 16.4 lack constructable stylesheets, so the JSON editor would lose its styling there. They are outside the supported list.
- In the dense documents table and column chooser, checkbox hit areas are 32px at `lg` and above (44px below `lg`), so a box never reaches the next row's box.

The hardening audit passed with no CRITICAL, HIGH or MEDIUM findings. These LOW findings were accepted for now:

### Open security findings (LOW, from the Phase 5 audit)

The Phase 5 security audit passed with no CRITICAL, HIGH or MEDIUM findings. This LOW finding was accepted for now:

### Resolved before Phase 5

The pre-Phase-5 hardening closed these findings and gaps. Each is checked by the acceptance criteria (AC) of that work:

- **P2-SEC-1:** `orderBy` and every filter key must be a plain identifier, or `validateListParams` rejects the params with `ERR_CLIENT_VALIDATION` and no request is sent (AC-1 to AC-4). See [Content data](./content-data.md).
- **P2-SEC-2:** `search` and string filter values are capped at 256 characters (`MAX_LIST_TEXT_LENGTH`), with the same fail-closed rejection (AC-5 to AC-7). See [Content data](./content-data.md).
- **SEC-3:** the Bearer token goes only to requests for the API origin, on the first try and on the retry after a refresh (AC-20, AC-21). See [API client](./api-client.md).
- **SEC-4:** the nginx image serves `Content-Security-Policy` (built from `CSP_API_ORIGIN` and `CSP_IMG_ORIGINS`) and `Referrer-Policy: same-origin`, and `index.html` sets a `same-origin` referrer meta. The `csp` Playwright project checks the built app under the policy (AC-8 to AC-13). This also closes the Phase 3 CSP gap and the Phase 4 `img-src` gap. See [CSP and headers](./csp-and-headers.md).
- **SEC-5:** the reset page reads the token once and strips it from the URL without adding a history entry (AC-14 to AC-16). See [Onboarding and recovery](./onboarding-and-recovery.md).
- **P4-SEC-2:** thumbnail URLs pass an allowlist (`https:`, the API origin or the page origin) and load with `referrerPolicy="no-referrer"`; anything else shows a placeholder (AC-17 to AC-19). See [Settings media](./settings-media.md).
- **Phase 3 gap:** the mobile menu drawer is marked `aria-modal="true"` (AC-22).

### Deferred to Phase 5 (closed)

- The schema-aware "known column" check shipped in Phase 5: `validateListParamsForType` in `columns.ts` allows `orderBy` only on a sortable column and filters only on a filterable column with an allowed operator. The list URL parser drops anything else (D8), and `useDocumentList(ref, params, catalog)` fails closed with `ERR_CLIENT_VALIDATION` before any request. See [Documents list](./documents-list.md#known-column-check).
