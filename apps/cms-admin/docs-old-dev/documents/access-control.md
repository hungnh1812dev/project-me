# Access Control (Users, Roles, Permissions, Access Tokens)

`src/pages/admin/settings/{UsersPage,RolesPage,PermissionsPage,AccessTokensPage}.tsx`, `src/hooks/{useUsers,useRoles,usePermissions,useAccessTokens}.ts`, `src/components/permissions/{PermissionTree,permissionGrouping}.ts` — the four settings screens that manage who can do what, all now driven entirely by live, DB-backed data — there is no hardcoded role/permission vocabulary anywhere in this module anymore. `UsersPage` routes at `minLevel={ROLE_LEVEL.ADMIN}`, the other three at `minLevel={ROLE_LEVEL.SUPER_ADMIN}` (see [app-shell.md](./app-shell.md)'s router table), and are additionally sidebar-gated by permission slug (see [navigation-shell.md](./navigation-shell.md)).

## Button-level permission gating (`lib/permissions.ts`, `components/permissions/PermissionTooltip.tsx`)

Every mutating action button across the admin (not just this module) is gated client-side on the current user's granted permissions, in addition to the backend's own enforcement — defense-in-depth, not a substitute for it. `hasPermission(granted, required)` mirrors the backend's `:manager`-satisfies-`:read` equivalence (`PermissionsGuard.managerEquivalentOf`); `hasDocumentPermission(granted, action, contentTypeSlug)` mirrors `isDocumentActionGranted` (see [content-type.md](./content-type.md)/[documents.md](./documents.md) for the scoped `document:<action>:<slug>` form used by content-type/document actions). `usePermissionGate(required, contentTypeSlug?)` wraps both behind one hook — bare mode without `contentTypeSlug`, scoped mode with it — returning `{ allowed, reason }`. `<PermissionTooltip required contentTypeSlug?>` composes the hook with a `ui/tooltip.tsx` (Base UI) tooltip: when denied, it wraps the child in a focusable `<span>` and disables it with the `reason` shown on hover (a truly `disabled` DOM element doesn't reliably fire tooltip hover/focus events); when allowed, it renders the child unmodified. This gates Revoke/Delete on `AccessTokensPage` (`api_token:manager`), Create/Edit/Delete on `RolesPage` (`role:manager`) and `PermissionsPage` (`permission:manager`), Upload/Delete on the media pages (see [media.md](./media.md)), and the scoped document actions on collection/content-type pages (see [documents.md](./documents.md), [content-type.md](./content-type.md)). `UsersPage` predates this primitive and keeps its own bespoke `myLevel`-comparison gating (see below), not `PermissionTooltip`.

## Dynamic role hierarchy (replaces the old `lib/roles.ts`)

The former hardcoded `roleLevel` map (`{ super_admin: 4, admin: 3, editor: 2, guest: 1 }`) and `ALL_ROLES` array are gone — `lib/roles.ts` was deleted entirely. Every screen that needs "is this role higher/lower than that one" now compares live `RoleItem.level` (an admin-configurable integer, not a fixed enum) fetched via `useRoleList()`. `UsersPage`'s role-change dropdown, for example, filters to `roles.filter((role) => role.level < myLevel)` computed against the caller's own live `role.level` — a role created through `RolesPage` with any name/level shows up correctly everywhere, with no separate list to keep in sync.

## Users (`UsersPage`, `hooks/useUsers.ts`)

Unpaginated list — `GET /users` returns every `UserItem` (`documentId`, `email`, `name`, `username`, `accountType`, `verified`, `roleId`, timestamps; no embedded role object, joined client-side against `useRoleList()`'s `documentId`). Role change is `PATCH /users/:id/role` with `{ roleId }` (`useUpdateUserRole`); delete is `DELETE /users/:id`. Both actions are restricted client-side to rows where `!isMe && myLevel > (userRole?.level ?? 0)` — a same-or-higher-level peer can't be managed from this UI (server-side enforcement is separate, not documented here). There is no invite flow embedded here anymore — see [locales-and-invites.md](./locales-and-invites.md).

## Roles (`RolesPage`, `hooks/useRoles.ts`)

Full CRUD over `/roles`. `RoleItem` is `{ documentId, name, slug, permissions: string[], level, isDefault }`. `isDefault` roles have their `name`/`level` fields disabled in the edit dialog (permissions remain editable even for default roles); `slug` is immutable after creation in both create and edit. Level range is UI-enforced 1–99 (`<input type="number" min={1} max={99}>`, not further validated). `RoleDialog`'s permission picker is the shared `PermissionTree` (see below); `PermissionSubTree` (the read-only, expand-to-view summary shown in the roles table) stays local to `RolesPage.tsx` — it's a display-only variant with no selection state, not worth sharing.

## Permissions (`PermissionsPage`, `hooks/usePermissions.ts`)

Full CRUD over `/permissions` — the permission-slug catalog itself, not role assignments (that's `RolesPage`'s `PermissionTree`). `PermissionItem` is `{ documentId, slug, name, description }`. Slug format is enforced client-side via `SLUG_PATTERN = /^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$/` (`resource:action`) and is immutable after creation. A dedicated info line makes explicit that creating a permission slug here **grants nothing by itself** — a developer must add a matching server-side check before it does anything. Delete failures (e.g. a permission still referenced by a role or access token — the API returns a structured `{ roleCount, accessTokenCount }` conflict body, parsed by `extractErrorMessage`) surface per-row via `deleteErrors` state rather than a global toast, the only settings page that does this.

## Shared `PermissionTree` (`components/permissions/PermissionTree.tsx`)

Extracted out of `RolesPage` during this rewrite so `AccessTokensPage` could reuse it instead of hand-rolling a second tri-state picker (see below). Pure `{ permissions: PermissionItem[], selected: string[], onChange }` component: a tri-state (checked/indeterminate/unchecked) checkbox tree grouped by `resourceOf(slug)` (text before the first `:`, via `components/permissions/permissionGrouping.ts`'s `groupByResource`/`resourceOf`), with a top-level "Select All" and a per-group toggle-all. No Roles- or AccessTokens-specific coupling — both `RoleDialog` and `AccessTokensPage`'s create dialog pass it the same live `usePermissions()` catalog.

## Access Tokens (`AccessTokensPage`, `hooks/useAccessTokens.ts`)

Unpaginated list — `GET /access-tokens` returns every `AccessTokenItem` (`documentId`, `name`, `permissions: string[]`, `expiresAt`, timestamps, `updatedBy`; **no secret**). The scope picker is now the shared `PermissionTree` driven by `usePermissions()` — the old hand-built `DOCUMENT_ACTIONS`/per-content-type scope vocabulary (`document:read:<slug>` etc., independent of the `permissions:*`/`roles:*` catalog) is gone; access-token scopes and role permissions are the same vocabulary now, one system instead of two. Creation (`POST /access-tokens`, `{ name, permissions, expiresIn }`) takes an `ExpiresIn` enum (`"30m" | "1h" | "1d" | "1m" | "1y" | "never"`) instead of a raw duration. There is no update endpoint, but there is now **revoke** (`POST /access-tokens/:id/revoke`, `useRevokeAccessToken`) in addition to delete (`DELETE /access-tokens/:id`) — revoke rotates the secret and returns a fresh `AccessTokenSecret` (the item plus a plaintext `token` field), reusing the same `TokenRevealDialog` ("copy this now, it won't be shown again") that the create flow uses. Delete removes the token entirely; revoke keeps the token record but invalidates the old secret.
